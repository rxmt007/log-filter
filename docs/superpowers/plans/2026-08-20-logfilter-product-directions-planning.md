## 1. 目标

把机会调研中的 P0、P1、P2 与 P2/P3 边界方向整理成一份可离线打开、可筛选、可检索、可展开的交互式 HTML 规划文档。每个方向只给出一个明确产品方案，并完整说明用户问题、核心价值、主要交互流程、功能边界、依赖、风险、优先级与验证方式。

同时制作一个嵌入现有 LogFilter 主窗口的代表性“调查闭环”原型，帮助团队理解下一阶段产品形态：

> 确认采集可信 → 恢复调查方法 → 定位复现窗口 → 理解局部证据 → 保存调查状态 → 安全分享。

## 2. 范围与不变量

### 本计划会做

- 梳理 3 个 P0、7 个 P1/P1 验证、6 个 P2/P2-P3 边界方向，共 16 个方向。
- 为全部方向提供统一的八字段决策卡和唯一方案。
- 用一个统一原型串联适合当前可视化验证的七个方向：抓取健康度、命名调查配方、时间定位与范围、安全分享导出、可见范围结构化检查、密度/噪声摘要、调查会话。
- 对基础设施型或尚未通过事实验证的方向，只展示规划与必要状态反馈，不提前冻结错误 UI 心智模型。
- 延续现有 LogFilter 1180×860 桌面窗口、工具栏、过滤栏、小地图、密集日志表、底部状态栏和 Problems dock 形态。

### 本计划不会做

- 不修改 `src/`、`src-tauri/`、`crates/`，不增加 IPC，不实现任何产品功能。
- 不把原型中的 mock 交互描述为已实现能力。
- 不把 P1 验证方向写成产品承诺。
- 不纳入纯 P3“有界 AI 解释”；不做整份日志上云、默认 AI 根因、默认有损采集、远程日志平台、插件市场、完整 DSL/SQL 或前端多文件拼接。
- 不突破 `get_rows(..., count≤512)`、只传可见窗口、原始证据只读、单 Session 和 generation 等架构不变量。

## 3. 信息架构

交互式 HTML 采用一个页面、五个工作区：

1. **决策总览**：产品命题、排序原则、阶段数量、信任边界和核心不变量。
2. **路线图**：以“现在 / 下一步 / 探索”表达 P0/P1/P2，不承诺日期。
3. **方向浏览器**：优先级筛选、关键词搜索、只看验证项、统一方向卡、深链定位。
4. **依赖图谱**：展示时间分段、文件身份/provenance、流式导出、生命周期事实、MultiSource Session 等前置关系。
5. **调查闭环原型**：在同一 LogFilter 主窗口内演示核心路径，并明确标注“概念原型，不代表已实现”。

## 4. 视觉与交互原则

- 使用设计稿的浅/深色 token：`#3B82F6` 主强调、系统 UI 字体、等宽日志/时间/指标、1px hairline、6–9px 圆角和克制阴影。
- 日志表格仍是视觉主角；新增能力使用 context banner、下拉、对话框、底部 dock 和状态栏，不新增独立首页或永久侧栏。
- P0 使用实心蓝标签，P1 使用蓝色描边，P2 使用中性灰，避免占用日志级别红/橙/绿语义。
- 使用原生 `button`、`input`、`details` 等语义控件，提供键盘焦点、`aria-expanded`、`aria-pressed`、`aria-live` 和 Escape 返回焦点。
- 图标仅复用现有设计语言与 Lucide 图标路径；不引入图片占位符、装饰图或另一套图标风格。

## 5. 实施任务

### Task 1：建立规划数据模型

- 为 16 个方向建立统一数据项：编号、优先级、阶段、方案、八字段、验证门、原型覆盖标记。
- 保持“产品事实 / 产品推断 / 验证假设”边界清楚。
- 将 P2/P3 多文件方向放在 P2 边界探索中，并标明引擎级 MultiSource Session 前置。

### Task 2：制作单文件规划文档

- 新增 `docs/design/product-directions/index.html`。
- CSS、JavaScript、方向数据和 Lucide 图标符号全部内联；不使用 CDN、远程字体、`fetch`、XHR、动态 import 或外部脚本。
- JavaScript 只做渐进增强；规划正文在脚本失败时仍可阅读。
- 支持 P0/P1/P2 筛选、关键词搜索、展开/折叠、hash 深链、主题切换和减少动画偏好。

### Task 3：制作调查闭环代表性原型

- 保持 1180×860 LogFilter 窗口基准。
- 在现有结构中加入健康状态、配方选择、时间范围、密度 dock、结构化详情、调查会话和安全导出。
- 原型交互仅更新内存中的 mock 状态，不读文件、不调用 ADB/IPC、不访问网络。
- 未进入原型的方向仍在规划卡中给出唯一形态和明确依赖。

### Task 4：浏览器与离线 QA

- 在 1440×900、1024×768、390×844 检查布局；桌面原型只在自身容器内横向滚动。
- 验证主题、筛选、搜索、展开、深链、配方、时间范围、密度跳转、结构化详情、调查保存和安全导出流程。
- 用相同 1180×860 状态比较设计稿与原型：字体、间距、颜色、圆角、边框、层级、内容密度和交互状态。
- 以 `file:` 文档 URL 在本地运行时检查解析与核心交互；浏览器视觉则用仅含该 HTML 的隔离目录检查零附加资源、零控制台错误。
- 生成 `docs/design/product-directions/design-qa.md`，记录比较证据、修复历史和最终结果。

### Task 5：范围、隐私与仓库验证

- 确认 Git diff 仅位于 `docs/`。
- 扫描真实姓名/拼音、真实本地路径、真实内网 IP、设备 serial、凭据和敏感 token；示例统一使用 `QA Device · DEMO-0001`、`com.example.demo`、`example.com`、`192.168.x.x`。
- 运行仓库完整验证全集：Rust tests、clippy、fmt、TypeScript typecheck、lint、Vitest。
- 由独立评审检查方向覆盖、功能边界、离线性、交互可达性和视觉一致性。

## 6. 完成定义

- 16 个方向均有且只有一个方案，并具备完整八字段。
- 代表性原型可从采集健康一路走到安全分享，所有核心操作可键盘完成。
- HTML 可单文件离线打开，不依赖 `support.js`、Google Fonts、unpkg 或任何网络资源。
- 视觉 QA 无遗留 P0/P1/P2 问题，`design-qa.md` 的 `final result` 为 `passed`。
- Git diff 仅包含 `docs/` 下的规划与必要设计资源，隐私扫描和完整验证全集通过。
